# Решение: готовая CRM для первого пилота

Дата: 2026-10-28. Цель пользователя: простой CRM-блок и автоматизация сбора информации; самостоятельно выбрать готовое open-source решение вместо повторного написания CRM.

## Выбор

**EspoCRM 10.0.11 — готовое CRM-ядро для локального пилота «Мэджик Металл».** Использовать штатные компании, контакты, заметки, задачи, поиск и настройки. Существующий SAAS сохранить как самостоятельный продукт и возможный интеграционный слой; не удалять его код, не переносить production, не встраивать AGPL-код в собственный backend механическим копированием.

Это выбор для одной компании, а не подтверждение готовности общей мультитенантной SaaS-платформы. До проверки изоляции независимые компании нельзя помещать в одну общую базу под видом tenant-изоляции. Для отдельного пилота достаточно отдельного экземпляра и БД; массовая SaaS-эксплуатация пока не утверждается.

Причина выбора: требуемая CRM-цепочка уже существует и фактически проверена в локальной установленной версии. Нет необходимости повторно реализовывать её сущности и CRUD. Ускорение в днях или процентах не измерялось и не заявляется.

## Что реально запущено и проверено

Официальный образ: `espocrm/espocrm@sha256:8e1c7e97e0a1a08953a86af89c3808cb95410b6a5eb487d1e3475d2c7289357d`.
Версия приложения через штатную CLI: **10.0.11**. Соответствующий Git tag: `10.0.11`, commit **32d559ba86d3be607599d1325c359668c1178850** (annotated tag object `61391dabe5a20e27e916c2cdf31f2bc3909f177d`).

Источник сущностей в этом релизе:

- `application/Espo/Modules/Crm/Entities/Account.php`, `Contact.php`, `Task.php`;
- `application/Espo/Modules/Crm/Resources/metadata/entityDefs/Account.json`, `Contact.json`, `Task.json`;
- `application/Espo/Core/Acl/DefaultAccessChecker.php` — наличие ACL, не доказательство tenant-изоляции.

Работают локально: EspoCRM + отдельная MariaDB 10.11. CRM-порт привязан только к loopback. Синтетические данные, никаких production-записей, SMTP/платежей/реальных сообщений.

Первоначальная попытка по README с whole-root volume дала HTTP 500: в образе 10.x пустой whole-root volume выбирает legacy-ветку entrypoint и пропускает новую установку; это не доказательство невозможности запуска всех существующих legacy-инсталляций. Диагноз подтверждён `docker-entrypoint.sh:isLegacy/actionInstall` официального docker-репозитория, HEAD `a2f3e9cba6edb596afdafca2b9ac6d639fd29c5c`. Исправлено отдельными томами `custom`, `data`, `client/custom`; старый том сохранён, данные не удалялись. Вход и штатный app-check после этого успешны. Сохранённый compose использует digest, а не mutable latest.

### API, без mocks

`verify-chain.py`: PASS для пяти проверок:

1. Создать компанию и прочитать её по ID.
2. Создать контакт и проверить связь с компанией после повторного чтения.
3. Создать заметку Stream/Post на контакте и прочитать сохранённый текст.
4. Создать связанную с контактом задачу, указать ответственного и срок; проверить после чтения.
5. Найти компанию текстовым поиском.

Повторный запуск сначала выявил HTTP 409 для повторного тестового контакта с тем же email. Это поведение защиты от дублирования, не ошибка установки. Тест исправлен: уникальные имена/email на каждый прогон. Повторный прогон PASS. Первый и второй наборы фикстур остаются локально; никаких реальных клиентов в них нет.

### REA, реальный браузер

Установленная REA 6.8.0, официальный Node 24.22.1, Chromium. Схема установленного CLI отличается от документации текущего upstream: неподдерживаемые `save_response`, `exact` и отсутствующий `wait_until` сначала были отклонены; сценарий исправлен по диагностике, без обхода валидации.

- `company-evidence.json`, Evidence **ev_a035536769f5f87a7e7e6257264586d67830a0e64ab150d2b56a69e831dcade7**: 15 шагов completed. Вход → форма компании → имя/сайт/email → сохранение через UI → переход в список → повторное открытие сохранённой карточки. Данные реально отправляются в локальный EspoCRM. Это проведённый здесь REA-анализ, не чужой отчёт.
- `chain-read-evidence.json`, Evidence **ev_a099efecb8eb397eda896f1886b7f0a3dc304365c61fb0e9ca331ac5d093769d**: 11 шагов completed. Вход и открытие сохранённых карточек компании, контакта и задачи. Связанные записи были созданы API-тестом; создание контакта/задачи/заметки через UI этим REA-сценарием не проверяется.
- Bodies/значения headers не записывались; локальный пароль передавался REA через secret reference и редактируется в Evidence. API тесты и REA наблюдения различаются.

Штатными CLI командами настроены `language=ru_RU`, `defaultCurrency=RUB`, `timeZone=Asia/Yekaterinburg`, очищен cache. Это локальная настройка пилота, не production.

## Автоматизация сбора информации

Готовая CRM не равна готовому поиску клиентов в интернете. В этом пилоте НЕ подтверждены DaData, сбор контактов с сайтов, PDF/Excel recognition, LLM, email sync или фоновые enrichment jobs. Они не подменяются фиктивной интеграцией.

Первый приём заявок выполнен штатным LeadCapture (проверка ниже). Следующее отдельное обогащение реквизитов: ввод ИНН/импорт → запрос разрешённого источника → поля с источником и временем получения → просмотр менеджером → запись через EspoCRM API. Не считать автоматически проверенными телефон/email, которых источник не предоставил. Запись не должна затирать вручную подтверждённые поля; запросы/обновления должны быть идемпотентны. Доступ к DaData пока блокируется активной сетевой политикой, хотя требование и домен сохранены в draft.

## Лицензия и границы

EspoCRM — AGPLv3 с требованиями к notices. Для сетевого использования модифицированного покрытого кода нужно выполнить применимые условия предоставления соответствующего исходного кода пользователям. Не обещается закрытый proprietary fork. Сохранять upstream и расширения отдельно, учитывать условия каждого add-on; платные дополнения не подключались. Подключение отдельного собственного приложения через API не даёт автоматического юридического заключения о лицензировании всей системы.

## Что не готово

Нет production deploy, резервного восстановления, менеджерского usability-теста, теста ролей/межклиентской изоляции, безопасности всех расширений, нагрузочного сравнения, устойчивых очередей и проверенного автоматического enrichment. EspoCRM выбран для локального пилота, а не объявлен готовым коммерческим SaaS.

GitHub API остаётся заблокированным прокси; PR/CI_GREEN не заявляются. Изменения выбора и Evidence сохраняются в отдельной ветке. Существующие SAAS-ветки и production не изменены.


## Дополнительная проверка агентами и native LeadCapture

По явному запросу пользователя подключены два параллельных агента. Первый независимо проверил выбор и лицензионные границы, второй исследовал готовый сбор информации. Их отчёты: independent-selection-review.md и collection-source-review.md. Они не изменяли сервисы, production или исходники; окончательные runtime-проверки выполнил основной агент.

Замечания ревью учтены: API-тест дополнен проверкой assignedUserId, parentType задачи и parentId/parentType заметки; повторный прогон PASS (chain-repeat-result.json). Уточнена причина сбоя первой Docker-установки, без обобщения на все legacy-инсталляции.

Повторный REA-прогон русской версии сначала не завершился: компания с новым именем, но прежним email вызвала предупреждение о дублировании, ожидание сохранённой карточки истекло. company-duplicate-failed-evidence.json сохраняет этот результат; завершённые шаги не объявляются полным успехом. prepare-scenario.py теперь автоматически задаёт уникальные имя и email. После исправления фикстуры русский сценарий прошёл все 15 шагов, Evidence ev_95068922250d7ca816abe07948415de2d1635742ea85d612fb04af06dbba2166 (company-ru-evidence.json).

Нативный приём заявок не пришлось разрабатывать. verify-capture.py реально проверил установленный EspoCRM10.0.11, без mock API:

- Создание синтетического лида через штатный публичный LeadCapture endpoint, без admin auth на самом запросе заявки.
- Источник Web Site задаётся сервером; подставленные извне source/status/assignedUserId не изменяют заданное поведение.
- Повторная последовательная отправка того же email не создаёт второй лид.
- Журнал содержит событие создания и событие дубликата.
- Отсутствующие обязательные поля отвергаются.
- Отключённый capture отвергает следующую заявку.

Все 7 проверок PASS, capture-result.json. Почтовые подтверждения и подписки отключены исключительно для синтетического локального теста. Созданный тестовый capture оставлен неактивным; его API key не сохранён в Git или отчёте. Скрипт при повторном запуске создаёт новую тестовую конфигурацию и снова отключает её в успешном конце; при падении следует проверить оставшийся local capture, не публиковать его автоматически.

Это НЕ тест конкурентных запросов/атомарной идемпотентности, не подключение сайта Magic Metal, не DaData/скрейпинг и не tenant-isolation. Автоматизированный первый сбор входящих заявок подтверждён; обогащение из независимых источников — нет. Вместо нового CRM-intake backend используем штатный LeadCapture; для production остаются защита публичной формы, consent, outbox/retry, ограничения и мониторинг.
